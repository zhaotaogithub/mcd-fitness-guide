# 减脂期麦门指南

## 这个 Skill 解决什么问题

减脂最难的不是「不吃」，是「想吃的时候不知道怎么吃」。

麦当劳的公开营养数据早就有了，但没人帮你把它和**你今天的剩余热量预算**、**门店实际在售的商品**、**你手里真实的优惠券**三者算在一起。所以大多数人的做法是：打开 App 看一眼热量表，凭感觉点一个麦香鸡，然后回家后悔。

这个 Skill 干的事只有一件——**把你今天的剩余热量预算，翻译成一份此刻这家门店就能下单、且最省钱的麦当劳订单。**

## 核心原则

1. **热量优先，但不唯热量。** 同样 500 kcal，一份「板烧鸡腿堡 + 无糖可乐」远优于「大薯条 + 麦旋风」。蛋白质要够、钠要控。
2. **数据必须来自 MCP，不许编。** 所有热量/营养/价格/券，一律实时查询。绝不凭记忆报数字。
3. **配餐必须能落地。** 只推荐**当前门店在售**的餐品，并在下单前用 `calculate-price` 核验真实到手价。
4. **不鼓励极端节食。** 若用户预算低于 400 kcal（一餐），提示风险并建议拆成两餐，不要硬凑一份「最便宜的低卡组合」。
5. **不做医疗建议。** 本 Skill 提供的是营养数据整理与配餐计算，不构成医疗或营养处方。有疾病史的用户请遵医嘱。

## 工作流

### 第 0 步：确认三个输入（缺一不可）

在开始配餐前，必须拿到：

| 输入 | 说明 | 缺失时怎么办 |
|---|---|---|
| **剩余热量预算** | 单位 kcal，本餐可用 | 问用户；或按 `references/budget-guide.md` 的日均 1800 kcal、三餐 4:4:2 粗略推算并**明确告知这是估算** |
| **就餐方式** | 到店自取 / 得来速 / 麦乐送 | 默认到店自取（beType=1），但必须告知用户 |
| **位置或门店** | 城市 + 地标，或直接给 storeCode | 问用户，不要瞎猜门店 |

同时可选采集：**目标蛋白质**（默认按体重 1.6 g/kg 估算）、**忌口**、**预算上限（元）**、**是否可用优惠券**。

> 若用户只说「我在减脂，想吃麦当劳」，不要追问超过 2 轮。用默认值跑一版，把假设写在结果里，让用户改。

### 第 1 步：拿营养基线

调用 `list-nutrition-foods`（无入参），得到 160 项餐品的能量、蛋白质、脂肪、碳水、钠、钙。

如果需要知道用户账户里有什么券，调用 `query-my-coupons`；想知道能领什么券，调用 `available-coupons`。

**这一步之后，你手里应该有两张表**：一份营养表，一份券表。

### 第 2 步：跑候选筛选（用脚本，不要手算）

把第 1 步拿到的营养表和用户预算，交给 `scripts/pick_meals.py`。它会：

- 过滤掉超出单餐预算的餐品
- 按「蛋白质密度」和「热量性价比」给主餐排序
- 输出 3 档方案：**保守（约 70% 预算）**、**标准（约 90%）**、**放开（约 100%）**

```bash
python scripts/pick_meals.py --budget 550 --protein 30 --data nutrition.json
```

脚本的详细参数与输出格式见 `references/calculation-rules.md`。

### 第 3 步：锁定真实门店与在售商品

1. `query-nearby-stores`（searchType=2，city + keyword，beType=1）拿到 `storeCode`
2. `query-meals`（storeCode + orderType=1 + beType=1）拿到**当前在售**商品及其 `productCode`

> ⚠️ 脚本给出的是「营养上合理」的候选；`query-meals` 给出的才是「此刻买得到」的。**两者取交集**，交集为空就换门店或换方案。

### 第 4 步：叠券比价

1. `query-store-coupons`（该门店 + 该订单类型）拿到**真正可用**的券
2. 注意区分：`query-my-coupons` 是「我有什么券」，**不做门店与渠道校验**；`query-store-coupons` 才是「这单能用什么券」
3. 把候选商品 + 可用券交给 `calculate-price`，拿到**真实应付总价**
4. 如果有多个券可用，**分别算一遍**，选实付最低的那个组合

### 第 5 步：出方案

输出一份可直接照做的点餐单。格式见下方「输出模板」。

### 第 6 步（可选）：确认后下单

只有用户**明确说「下单」**时才调用 `create-order`。下单前必须复述：门店、商品、数量、实付金额。
**绝不在用户没确认时下单。**

## 配餐经验规则

这些是**启发式，不是硬规则**——用于排序，不用于编造数据：

- **主餐优先选烘烤类**：板烧鸡腿堡（391 kcal）优于麦辣鸡腿堡（485 kcal）优于巨无霸（513 kcal）
- **麦满分系列是早餐里的低卡区**：烟肉蛋麦满分 260 kcal，火腿扒麦满分 261 kcal
- **饮品是最容易省下 200+ kcal 的地方**：可乐中杯 147 kcal → 无糖可乐 0 kcal，一键省下整份小薯条
- **薯条按尺寸换算**：迷你 106 / 小 210 / 中 289 / 大 379 kcal。想吃过瘾选迷你或小
- **麦乐鸡比想象中划算**：5 块 213 kcal、蛋白质 12g，脂肪 12g 偏高但可控
- **警惕「低卡错觉」**：玉米杯（小 53 kcal）很干净，但苹果片（32 kcal）更干净；反过来，新地/麦旋风 240-300 kcal 且几乎全是糖
- **钠是最容易被忽略的指标**：巨无霸 961mg、麦辣鸡腿堡 1208mg。若当天已吃过重口味的，优先选钠低的

## 边界与拒答

- **不编造数据。** 所有数字必须来自 MCP 调用。若某个工具调用失败，明确告知用户「这项数据没查到」，不要用记忆里的数字补位。
- **不替代医嘱。** 用户提到糖尿病、肾病、高血压、孕期、进食障碍，一律建议咨询医生/营养师，只提供数据不提供处方。
- **不诱导超量消费。** 用户预算很小时，不要为了凑单或凑券去推荐更多餐品。
- **不承诺减重效果。** 只做营养数据整理与配餐，不做减重承诺。

## 资源文件

- `scripts/pick_meals.py` —— 按热量预算与蛋白质目标筛选餐品组合，输出三档方案
- `scripts/nutrition_parse.py` —— 把 `list-nutrition-foods` 的返回原文解析成结构化 JSON
- `references/mcp-tools.md` —— 本 Skill 用到的 MCP 工具清单、入参、调用顺序与踩坑点
- `references/calculation-rules.md` —— 预算推算公式、蛋白质目标公式、排序权重、示例计算
- `references/budget-guide.md` —— 不同人群的日均热量与三餐分配参考表

## 快速示例

**用户**：我在减脂，今天还剩 550 kcal 想吃麦当劳，人在北京三里屯。

**你应该做的**：
1. 调 `list-nutrition-foods` → 拿到营养表
2. 调 `query-nearby-stores`(searchType=2, city="北京市", keyword="三里屯", beType=1) → 拿 storeCode
3. 调 `query-meals`(storeCode, orderType=1, beType=1) → 拿在售商品
4. 跑 `pick_meals.py --budget 550 --protein 30` → 拿候选
5. 取第 3 步与第 4 步的交集
6. 调 `query-store-coupons` + `calculate-price` → 拿真实价格
7. 按「输出模板」出方案

**关键**：第 1 步之前不要报任何数字；第 6 步之前不要报任何价格。
